**关于色彩,这次不锁死具体色值**——`DESIGN.md` 里的金/暖黑配色是现状,不是必须遵守的红线,这轮可以重新设计一套配色。真正的硬性要求只有一条:

## 3. 真实内容数据(不是占位数据,直接来自生产 API)

**重要**:免费/锁定两种状态的比赛,拿到的字段是不一样的(见下面两个真实响应)。设计稿必须覆盖这两种状态,不能只设计"数据齐全"那一种。

### 3.1 计数条数据源

`GET /api/v1/matches?status=upcoming&window=today|tomorrow|7d&limit=…` 的 `total` 字段,当前真实值:

```json
{ "今晚": 0, "明天": 1, "未来7天": 78 }
```

今晚/明天经常是 0(赛季间歇期是常态,不是 bug),UI 必须扛得住"今明两栏都是 0"这种情况——现有实现在此时会额外提示"今明暂无可用比赛,最近比赛:…",设计稿需要覆盖这个空态。

### 3.2 重点比赛卡 —— 「锁定」状态(该联赛未持有权限,当前 78 场里 43 场是这种)

```json
{
  "match_id": 5803528,
  "league_id": 223,
  "date_utc": "2026-08-14",
  "kickoff_at_utc": "2026-08-14T10:00:00Z",
  "round": "2",
  "status": "NotStarted",
  "home": { "name": "东京绿茵", "name_en": "Tokyo Verdy", "crest_url": "/api/v1/media/team-crests/fotmob/6223.png?v=8bf0468b3be3" },
  "away": { "name": "柏太阳神", "name_en": "Kashiwa Reysol", "crest_url": "/api/v1/media/team-crests/fotmob/8699.png?v=271971f65306" },
  "win_probability": null,
  "requires_login": true
}
```

`win_probability` 为 `null` 是后端**主动不下发**(不是还没算出来)——`requires_login: true` 的比赛,服务端根本不计算这个字段,防止前端拿到真值再用 CSS 遮挡(`CLAUDE.md` §8.2 红线)。设计稿里这种卡必须诚实展示"没有概率可看",不能画三段空概率条或者打码效果。

### 3.3 重点比赛卡 —— 「免费」状态(五大联赛等,当前 78 场里 35 场)

```json
{
  "match_id": 5868011,
  "league_id": 87,
  "date_utc": "2026-08-15",
  "kickoff_at_utc": "2026-08-15T17:30:00Z",
  "round": "1",
  "status": "NotStarted",
  "home": { "name": "阿拉维斯", "name_en": "Deportivo Alaves", "crest_url": "…" },
  "away": { "name": "赫塔菲", "name_en": "Getafe", "crest_url": "…" },
  "win_probability": {
    "p_home": 0.4065,
    "p_draw": 0.3339,
    "p_away": 0.2597,
    "observed_at": "2026-08-12T00:34:47Z"
  },
  "requires_login": false
}
```

`win_probability` 三项由 Bet365 赔率去水折算得来,**必须**展示 `observed_at`(赔率采集时刻)——这是真实快照时间,不是"实时"数据,不展示会违反"不伪装数据新鲜度"的规则。当前真实数据这个时间戳经常是 20+ 小时前(赔率源采集有节奏限制,不是故障),设计稿要考虑"时间戳很旧"时文案怎么写得诚实又不吓跑用户。

### 3.4 完整字段清单(一张比赛卡能拿到的全部内容)

| 字段 | 说明 | 是否可能为空 |
|---|---|---|
| `league_id` → 联赛中文名 + 联赛队徽 PNG | `frontend/public/brand/leagues/{id}.png`,17 个联赛已有图,新联赛可能缺图 | 图可能缺(缺图时不占位、不画兜底图标) |
| `kickoff_at_utc` | 精确开球时间(UTC),前端转北京时间显示 | 少数比赛只有自然日没有精确时刻,此时为 `null` |
| `home` / `away` | 球队中文名、英文名、队徽 PNG(经后端媒体路由,同源,不直连第三方) | 队徽可能缺(降级成球队名缩写,已有 `TeamBadge` 组件处理) |
| `home_score` / `away_score` | 已完赛比分 | 未开赛为 `null` |
| `status` | `NotStarted` / `InPlay` / `Finish` | — |
| `win_probability.{p_home,p_draw,p_away,observed_at}` | 主胜/平/客胜概率(0–1 小数)+ 赔率观测时刻 | **锁定联赛或无赔率时整体为 `null`,禁止补 0 或猜测** |
| `requires_login` | 该联赛是否需要登录才能看完整内容 | — |
| `odds_coverage_tier` | `full_timeline`(完整赔率走势)/ `open_close_only`(仅两点摘要)/ `none` | — |

## 4. 硬性规则(不是"设计偏好",是产品红线,必须遵守)

这些不是这次重设计"可以考虑"的建议,是不能违反的约束——来自 `CLAUDE.md`,已经在生产环境跑过审计:

1. **不伪造紧迫感**:不用假倒计时、不虚构在线人数、不做诱导式弹窗、不用赌场式视觉语言(闪烁红绿、"必中"字样)。**真实开球倒计时是允许的**(基于真实 `kickoff_at_utc` 算,不是营销话术)。
2. **概率边界不能靠视觉遮挡实现**:锁定联赛的比赛,后端根本不返回 `win_probability`——设计稿不能画"三段概率条 + 一层模糊/锁图标盖上去"这种效果,因为真实实现里那三个数字从来没被发下来过,没有"值"可以模糊。锁定状态就是诚实地不画概率条,用文案说明"登录后查看"。
3. **必须展示数据时效**:任何概率/赔率相关内容,旁边必须能看到"赔率采集于 XX 时刻"这类时间戳(用真实 `observed_at`,不是当前时间、不是"实时更新"这种话术)。
4. **移动端优先,主动砍列不缩字号**(`DESIGN.md` §4 移动端规则)——窄屏不是把所有元素等比缩小,而是决定哪些内容在窄屏直接不放。
5. **深浅色单一 JSX 实现**,见第 1 节。
6. **图片/字体自托管**:队徽走 `/api/v1/media/team-crests/…`(同源代理,不直连 FotMob CDN);联赛队徽是本地静态 PNG(`frontend/public/brand/leagues/`);不依赖国内访问不稳定的外链资源。
7. **横向滑动区域不能撑出页面级横向滚动条**——这条现有 E2E 测试在 360/390/430/1280 四个宽度强制断言,新设计如果保留横滑交互,滑动容器本身可以横向滚动,但整个 `<body>` 不可以出现横向滚动条。

## 5. 今天这轮迭代的历史背景(仅供参考,不是必须保留的约束)

以下是今天在代码里试过的几个方向,列出来是给设计工具"看看已经探索过什么",**不代表这些决定必须原样保留**——如果 Claude Design 通盘设计后有更好的方案,以新方案为准:

- 概率条从"近期战绩胜平负圆点"改成了"Bet365 赔率折算的胜平负横向三段条"(三段条本身作为组件已经实现,`WinProbabilityBar.tsx`,可以直接参考现有视觉或推翻重画)。
- 联赛队徽先后试过放在卡片顶部一行、和联赛名一起放在"vs"正上方两种位置。
- 开球时间的字号和"倒计时"是今天临时加的,没有经过认真的信息层级设计,只是从"文字太小、缺紧迫感"这个反馈里现改的。
- 近期比赛横滑卡的宽度、对阵是"上下两行"还是"一行平铺",都是今天来回调整过的,没有定论,设计工具可以按整体节奏重新决定卡片密度和单卡信息量。

**换句话说**:今天的实现是"能跑但拼凑"的状态,不是要保护的既有设计——放心整体推翻重来。
